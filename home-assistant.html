What you get

Once connected, the integration is designed to create a main dashboard device and one sub-device per alarm, with entities you can use in automations, dashboards, and scripts.

📊

Sensors

Alarm state, name, fire time, snooze count, app version, sleep sound volume, and more.

🔘

Buttons

Dismiss, snooze, skip, unskip, and kill snoozed — available on the dashboard device and each per-alarm device.

🔁

Switches

Master arm toggle, per-alarm enable/disable, alert vibrate, and alert media loop.

🔊

Alert Media

Send an alert to the phone from any HA automation using the notify service. Works like an alarm — shows an in-app alert card with a dismiss button — but is text-based and can include unauthenticated media URLs.

🚨

Send Alert

Send an alert to the phone from supported HA automations using the notify service. The entity is named Send Alert.

⏰

Per-Alarm Devices

Each alarm can appear in Home Assistant with its own related entities and supported controls for time, days, sound, snooze, and more.

🌙

Sleep Sounds

Start, stop, pause, or change white noise and ambient sounds on the phone from supported automations when app and iOS conditions allow.

🔐

Alarm Widget

Your security alarm, your home, one tap. When you arm a zone in Allarise, Home Assistant knows about it instantly — triggering automations, locking doors, or whatever you've set up. And since zones sync across all your household's phones, everyone stays on the same page.

⚡

Commands

Commands are named MQTT triggers you define in the app. When fired, Allarise publishes to their topic in Home Assistant so your automations can react. Assign them as swipe actions on alarm rows, swipe commands in the alarm widget, a tappable list, or buttons on the Notes page that follows an alarm once you've dismissed it.

1

Install the HACS integration

Via HACS (recommended)

  1. In Home Assistant, go to HACS → Integrations → ⋮ → Custom repositories
  2. Add https://github.com/domoretechnet/allarise-hacs-beta and select Integration as the category
  3. Find Allarise in the HACS store and click Download
  4. Restart Home Assistant
🧪 Beta integration. This is the allarise-hacs-beta repository, which tracks the TestFlight build. If you already have the release integration installed from allarise-hacs, remove it first — HACS cannot install two integrations that share the allarise domain.

Manual install

  1. Copy custom_components/allarise/ into your HA config/custom_components/ directory
  2. Restart Home Assistant
ℹ️ HACS must be installed in your Home Assistant instance. If you haven't set it up yet, visit hacs.xyz for installation instructions.
2

Set up your MQTT broker

Create a dedicated MQTT user for the Allarise app and restrict it to only the topics it needs. This keeps the app isolated from the rest of your broker.

Step 2a — Create a dedicated user

Open Settings → Add-ons → Mosquitto broker → Configuration and add a login under the logins key:

Mosquitto broker config 
logins:
  - username: allarise
    password: "your_secure_password"
customize:
  active: true
  folder: mosquitto

Save and restart the Mosquitto add-on after making this change.

3

Connect the Allarise app

In the Allarise iOS app, go to Settings → Home Assistant Integration and turn it on, then tap MQTT Settings. The app separates broker configuration into two sections — one for when you're on your home network, and one for when you're away.

MQTT Identity

Topic Prefixallarise (default) — must match what you enter in the HA integration in Step 4
Device NameiPhone (default) — change this to identify multiple phones; must also match Step 4
⚡
Turn on Allow Inbound Commands. This is what makes the integration two-way. Without it, Allarise will publish state to Home Assistant but won't accept any commands back — no alarm creation, no alerts, no remote actions. Make sure this is enabled or you'll only get half the integration.

This also unlocks sleep sound control. With inbound commands on, Home Assistant can start, stop, pause, or change the white noise and ambient sounds playing on your phone — directly from any automation.

Internal Broker — used on home WiFi

Your Mosquitto broker running locally on Home Assistant. Plain connection, no TLS, traffic stays on your LAN.

HostYour HA local IP (e.g. 192.168.1.100) or hostname (e.g. homeassistant.local)
Port1883

External Broker — used away from home

Used when not on a home WiFi network. The app always enforces TLS for external connections. You'll need port 8883 forwarded on your router and pointing to your Home Assistant machine.

HostYour external hostname (e.g. mqtt.yourdomain.com) — must have a valid TLS certificate
Port8883
Always Use ExternalOptional — bypasses home network detection and always connects to the external broker
ℹ️ If you only use Allarise at home, you can leave the External Broker fields blank entirely.

Authentication

The same username and password are used for both brokers.

UsernameThe MQTT username you created in Step 2a (e.g. allarise)
PasswordThe password you set in Step 2a

Home WiFi Networks

Add your home WiFi network name(s) so the app can decide when to use the internal broker instead of the external one. Broker selection is designed to switch automatically when you leave or return home, based on the network information available to iOS.

  1. Tap Add Network
  2. Type your network name exactly, or tap Use Current Network to fill it in automatically
  3. Repeat for any additional home networks (e.g. separate 5 GHz and 2.4 GHz SSIDs)
📍 WiFi name detection requires Location permission on iOS. This is only used to read the network name — the app does not track your location.

Test your connection

Once all fields are filled in, tap Test Connection in the Authentication section. A green "Connected!" indicates the app was able to reach your broker at the time of the test.

4

Add the integration in Home Assistant

  1. Go to Settings → Devices & Services → Add Integration
  2. Search for Allarise and select it
  3. Enter the Device Name and MQTT Topic Prefix — these must exactly match what is set in the Allarise app
ℹ️ Defaults: Device Name = iPhone · Topic Prefix = allarise. You can add multiple devices by adding one integration entry per phone.

Exposes a media player entity that triggers a one-time in-app alert card on the phone — plays your chosen audio or TTS with a dismiss button. Supports play_media, media_announce, volume_set, and a Loop Media switch and Alert Volume number entity.

Send Alert (notify)

Send an alert to the phone using the standard HA notify service. The entity is called Send Alert on the device page — the entity ID is unchanged:

Send a full-screen alert 
service: notify.allarise_iphone
data:
  title: "Door Alert"
  message: "Front door opened"
  data:
    sound: "Perimeter_Breach"
    volume: 0.8
    media_url: "http://your-ha.local:8123/local/doorbell.mp3"
ℹ️ "Send Alert — Unknown" on the Notifiers card is not a fault. A notify entity's state is the time it last sent something, so it reads unknown until the first alert goes out and shows a timestamp after that.

Alarm IDs

Every alarm on the phone carries a number — its Alarm ID, also called the MQTT alarm index. It is what update_alarm and delete_alarm target, and it is the number in that alarm's entity IDs: sensor.allarise_iphone_alarm_3_state belongs to alarm 3.

Renaming an alarm is safe. The ID is assigned when the alarm is created and does not change when the alarm is renamed. Renaming updates the Home Assistant device name; the entity IDs stay keyed on the number. That is the whole point of the ID — automations written against it survive the alarm being renamed on the phone.

Three ways to find an alarm's ID

WhereWhat you look at
Home AssistantThe alarm's device page has an Alarm ID sensor, filed under Diagnostic. Easiest route.
Any entity IDThe number between alarm_ and the sensor name — …_alarm_3_fire_time is alarm 3.
The appOpen the alarm and scroll to the bottom of the edit screen: MQTT Alarm Index.

delete_alarm also accepts a name instead of an ID, and the automation editor offers the phone's alarms as 3 — Weekday Wake so you rarely have to look the number up by hand.

⚠️ "Reset MQTT Alarm IDs" renumbers everything. That button in the app's MQTT settings re-assigns every alarm's ID immediately, in time order. Home Assistant entities are keyed on those IDs, so an automation pointing at alarm 3 will silently start acting on whichever alarm is now number 3. The app spells this out before it does it. Renaming an alarm is safe; renumbering is not — expect to fix up your automations afterwards.

Audio: sleep sounds & radio

🔊 One audio channel, eight controls. The Sleep Sound and Radio Station dropdowns drive the same player on the phone — starting a station stops a sleep sound, and starting a sleep sound stops the station. There is one player, not two. That is why the two selects and the six transport buttons all carry an Audio: prefix and read as one group on the device page. Display names only; entity IDs are unchanged.

Sleep sounds (white noise, rain, fan, etc.) can be started, stopped, paused, resumed, and adjusted remotely from supported Home Assistant automations or scripts when app and iOS conditions allow. The current sound name and volume are published as sensors on the dashboard device and can also be surfaced in Home Assistant dashboards.

Dashboard sensors

SensorDescription
Sleep SoundName of the currently playing sound, or none
Sleep Sound VolumeCurrent playback volume as a percentage

Dashboard buttons

Three buttons appear on the main dashboard device for quick control:

ButtonAction
Sleep Sound StopFully stop playback and release the audio session
Sleep Sound PauseMute audio while keeping the session alive (lock screen controls remain visible)
Sleep Sound ResumeUnmute and resume from where it was paused

Commands

All sleep sound commands are sent via MQTT to the app's command topic. Available sounds: Brown_Noise, white_noise, Fan, Light_Rain, Summer_Rain, Sea_Waves, Mountain_Stream, Rainforest_Birds.

Start a sleep sound 
topic: allarise/iphone/command/sleep_sound_start
payload: |
  {
    "sound": "Brown_Noise",
    "volume": 60,
    "duration_minutes": 30,
    "fade_out_minutes": 5
  }

Payload keys (all optional except the command itself):
sound — sound name (defaults to first available if omitted)
volume — 0–100 sleep sound playback level (defaults to 50); unaffected by mute switch
system_volume — 0–100 iOS media volume (optional); sets hardware volume independently of volume
duration_minutes — play for N minutes, max 720; omit for indefinite
until_next_alarm — true to stop automatically when the next alarm fires
fade_out_minutes / fade_out_seconds — fade-out duration before stopping

volume vs system_volume: volume controls how loud the sleep sound plays within the app and is not affected by the ringer/mute switch. system_volume sets the device's hardware media volume (the same level shown in Control Center and adjusted by the volume buttons) — it affects all audio on the device, not just the sleep sound. Use both together if you want to, for example, start rain sounds at 60% app volume while also setting the phone to 40% system volume so other audio (like podcasts) doesn't blare at full volume.

Change sound without stopping 
topic: allarise/iphone/command/sleep_sound_change
payload: {"sound": "Sea_Waves"}
Adjust volume while playing 
topic: allarise/iphone/command/sleep_sound_set_volume
payload: {"volume": 40}
Stop playback 
topic: allarise/iphone/command/sleep_sound_stop
payload: {}
💡 Use until_next_alarm: true in sleep_sound_start to have the app attempt to stop white noise when the next alarm fires, without requiring a separate automation.

Radio

The app can also be driven as an internet-radio player, and each alarm can carry a wake-up station. The dropdown is filled from the stations you have favourited in the app, so favourites added or removed there appear and disappear on their own.

EntityDoes
Audio: Radio Station (select)Pick a favourited station to start it, or none to stop. Before the app's first publish arrives the dropdown offers only none — unlike sleep sounds there is no bundled set to fall back on.
Audio: Radio Stop / Pause / ResumeTransport buttons.
Radio Stateplaying / paused / stopped
Radio StationThe station playing now, or none

Publish to MQTT directly when you need something the dropdown cannot express — a sleep timer, a volume, or an arbitrary stream URL:

Start a station with a timer 
service: mqtt.publish
data:
  topic: "allarise/iphone/command/radio_start"
  payload: >
    {"station": "WDET", "until_next_alarm": true,
     "fade_out_minutes": 5}

station takes a favourited station's name or UUID, or an object {"url": "https://…", "name": "…"} for any stream. radio_start is ignored while an alarm is ringing.

A per-alarm wake-up station is set with the radio_station field on create_alarm / update_alarm. Send "" to clear it.

⚠️ Radio playback needs the app awake — see App Persistence. When iOS suspends the app the stream stops, and a radio alarm rings with its own tone instead of the station. Persistence On keeps it awake all the time. Under Dynamic the app is usually awake in the run-up to an alarm, so a radio alarm will normally get its station — but that depends on iOS waking the app, so it is a likelihood rather than a promise; choose On if a radio alarm must never fall back to its tone. Sleep sounds have their own keep-alive while playing and do not depend on this at all.

Group them on one card

App Persistence

App Persistence is the app's background keep-alive, and it is the single setting that decides how much of this integration works while your phone is in your pocket. It has three settings, chosen in the app under Settings ▸ Reliability.

SettingWhat happens
On
always ready		The app stays resident all night. A radio alarm streams its actual station, and MQTT keeps working — the phone answers commands without you opening it. Highest battery use.
Dynamic
ready when it matters		The app stays awake while the phone is charging, and in the run-up to your next alarm (about 75 minutes before). The rest of the time it sleeps and saves battery. In those awake windows you get the radio stream, custom volume and Home Assistant commands; outside them the phone behaves like Off until it wakes again.
Off
best battery		iOS suspends the app. A radio alarm plays its own tone instead of the station, and nothing on that phone answers MQTT until you open it. Lowest battery use.
⏰ Your alarm rings either way. This is true of all three settings. The alarm is scheduled with iOS itself, in every mode, so nothing here can stop it going off on time. What App Persistence changes is the quality of the wake-up — whether the app can use your custom volume, play a radio station rather than a tone, and answer Home Assistant.

Dynamic is a likelihood, not a promise. The app is woken in the background by iOS, and iOS decides when — and whether — that happens. Treat Dynamic as "usually awake while charging or near an alarm", not as a guarantee that the phone is reachable at a given moment. If you need a phone that always answers Home Assistant, choose On.

ℹ️ Everyone was moved to Dynamic. Dynamic is the default for new installs and existing users alike — including anyone who previously had persistence switched off. The app shows a one-time notice explaining the change. If you use MQTT: inbound commands now sleep with the app when it is off the charger and no alarm is near, and work while it is charging. Nothing about your alarms changed, and switching back to On in Settings ▸ Reliability restores always-on Home Assistant behaviour.

Entities

EntityValue
select.<device>_app_persistence_modeon / off / dynamic — the setting the user chose. This is the one to set from an automation.
switch.<device>_app_persistenceToggle between On and Off from a dashboard or automation
sensor.<device>_app_persistenceon / off — whether the app is awake right now. Under Dynamic this flips back and forth on its own, by design.
🔎 The select and the switch answer different questions. The select reports the mode you picked. The switch and sensor report whether the app is resident at this moment — which under Dynamic changes throughout the day as the phone charges or an alarm approaches. Neither is wrong; a phone can be set to Dynamic and be asleep, and the sensor saying off is the honest answer to "is it awake".

How you tell whether it worked

There is no reply to the command. The app publishes its setting back on its state topic, retained, on connect and on every change — including a command that asked for the value it already had — so an automation gets a definitive answer either way:

Wait for the phone to confirm 
- action: switch.turn_on
  target:
    entity_id: switch.bedroom_iphone_app_persistence
- wait_template: "{{ is_state('sensor.bedroom_iphone_app_persistence', 'on') }}"
  timeout: "00:00:15"
  continue_on_timeout: true
- condition: template
  value_template: "{{ not wait.completed }}"
# …the phone did not answer. Notify, or fall back.

The switch shows unavailable when the app cannot answer — either it is offline, or it has never published the setting. That is the honest answer rather than a stale value, and the unavailability is information.

⚠️ A sleeping app cannot be reached. With persistence Off this is absolute: turning it off is exactly what causes iOS to suspend the app, so there is nothing connected to receive the command that would turn it on again — off → on has to happen on the phone. Dynamic softens this, because a Dynamic phone wakes up by itself while charging and before an alarm, so a command sent during one of those windows can land. It is a better chance rather than a guarantee — outside those windows a Dynamic phone is as unreachable as one that is Off. Plan any "save battery overnight, restore in the morning" automation around that; it is the first thing people hit.

You can publish the command directly as well. ON, OFF, DYNAMIC and JSON all work on the same topic — DYNAMIC was added alongside the other two, so anything you already publish keeps working unchanged:

Raw MQTT 
action: mqtt.publish
data:
  topic: "allarise/iphone/command/app_persistence"
  payload: "DYNAMIC"

After sending DYNAMIC, watch sensor.<device>_app_persistence_mode rather than sensor.<device>_app_persistence. A phone that has just gone Dynamic off the charger with no alarm nearby will correctly report off for "am I awake", which is not the same as the command having failed.

ℹ️ Mismatched versions? An older app never publishes these topics, so the switch and the mode dropdown stay unavailable rather than showing a value they cannot back up — and if DYNAMIC reaches an older app it is simply ignored, never mistaken for "off". A newer app with an older integration publishes the extra mode topic to nobody, which is harmless; its switch keeps working as before, and now reflects whether the app is awake.

Fields that fill themselves in

The service fields in the automation editor offer what is actually on your phone instead of asking you to remember it:

FieldOffers
Device (every service)The Allarise devices configured here

Three things worth knowing, because each of them can look like a fault when it is not:

  • Every one of these is still free text. The list is a convenience — type any value and it is sent verbatim. Nothing that worked in YAML before stops working, and no automation is rewritten.
  • An empty list is normal, not an error: an older app publishes no sound inventory, and a phone that has not been seen since a restart has reported nothing yet. Type the value instead.
  • A command appears once the phone has published its status topic — the same moment it gets a Home Assistant sensor. One created seconds ago may not be listed yet. An editor page that is already open keeps the list it loaded with; reload it to pick up something new.
☑️ Toggle fields need ticking first. For every on/off field — Enabled, Vibrate, Morning weather, Verse of the Day, Play sound, One-shot, Show in list — tick the field to include it in the call, then use the toggle to set it. Left unticked, the field is not sent at all and the alarm keeps whatever it had. That is what makes "only change what I filled in" work.

allarise.update_alarm

Change an existing alarm. Only the fields you fill in are changed — everything else on the alarm is left alone. Target it by Alarm ID (see Alarm IDs); label renames it, and renaming never changes what an automation points at.

allarise.update_alarm 
service: allarise.update_alarm
data:
  device_name: iPhone        # optional if only one device
  index: 3                   # the alarm's Alarm ID — required
  time: "07:30"
  label: "Work Alarm"        # renames it; the ID stays the same
  enabled: true
  days: [monday, tuesday, wednesday, thursday, friday]
  sound: "Alarm_Clock"
  volume: 80                 # percent
  fade_in: 5                 # minutes
  snooze_interval: 9
  snooze_limit: 3
  notes: "Team meeting at 9am"
  morning_weather: true      # show Morning Weather card after dismissing
  dismiss_app_uri: "shortcuts://run-shortcut?name=Morning"

Days

The editor offers a weekday multi-select. Choosing none makes it a one-time alarm that fires once and then stops repeating.

In YAML, all of these are understood and mean the same thing:

Written asExample
Weekday namesdays: [monday, tuesday, wednesday, thursday, friday]
Numbers, 1 = Sunday … 7 = Saturdaydays: [2, 3, 4, 5, 6]
A comma-separated stringdays: "2,3,4,5,6"
Group wordsdays: weekdays · weekend · everyday
🐞 If your days never seemed to do anything, this is why. Older releases sent the string straight through and the app only ever read a list of numbers, so days: "2,3,4,5,6" quietly produced a one-time alarm and said nothing about it. Every shape above now works, and a day name that cannot be recognised is logged rather than dropped in silence.

Snooze and skip

How long a snooze lasts, how many are allowed, and how the buttons behave:

FieldValue
Snooze — snooze_intervalMinutes per snooze, 1–60. snooze_duration means the same thing and is accepted too.
Max snoozes — snooze_limitHow many snoozes before the alarm must be dismissed. 0 = snoozing not allowed. max_snooze_count is accepted too.
Snooze mode — snooze_modetap · hold · home_assistant (wait for HA to send a snooze) · disabled
Skip mode — skip_modetap · hold · disabled
Hold durations — snooze_hold_duration, skip_hold_durationSeconds the button must be held, 0.5–10. Only used in hold mode.

create_alarm shows the same two values under their app-side names, snooze_duration and max_snooze_count. Both services accept both pairs, so a payload copied between them keeps working either way round.

Missions

The editor has a Mission dropdown and a Mission difficulty dropdown beside it. Mission types: none (Tap, no challenge) · shake · math · balance_ball · block_drop (Bricks) · meteor (Meteor Defense) · home_assistant.

Set the mission and how hard it is 
service: allarise.update_alarm
data:
  index: 3
  mission: math
  mission_difficulty: hard

Set Mission in the same call as Mission difficulty. Difficulty on its own cannot be applied — changing the mission is what would clear the alarm's other missions, so the integration refuses to do it by implication and logs a warning instead. Super easy is a Math-only level; other missions fall back to Easy. Shake has no difficulty, so this sets its shake intensity (light / medium / vigorous).

⚠️ mission on its own clears the rest. Sending mission: math to an alarm that has three missions leaves it with math and nothing else — "set this alarm's mission" is taken literally, and it's what the Mission sensor reports back. To change one mission on a multi-mission alarm, send the full missions list.

An alarm can require up to five missions in sequence. missions and mission_config are not in the visual editor — they are YAML-only, because a list of objects is not something a dropdown can express. They are fully supported and are the way to build a chain or to configure a mission in detail:

Multi-mission alarm (YAML) 
service: allarise.update_alarm
data:
  index: 3
  missions:
    - mission: math
      mission_config:
        math_count: 3
        math_difficulty: hard
    - shake
    - mission: meteor
      mission_config:
        meteor_difficulty: easy

Each entry is either a bare type name or an object in the same shape as the single-mission form. Anything you put in mission_config yourself always wins over the Mission difficulty dropdown. The MQTT Payload Builder writes these payloads for you.

Fallback missions

A Home Assistant mission waits for Home Assistant to confirm the dismissal. If the broker is unreachable, the fallback is what the alarm asks for instead — so the alarm is always dismissible. It is configured through mission_config:

Home Assistant mission with a fallback 
service: allarise.update_alarm
data:
  index: 3
  mission: home_assistant
  mission_config:
    ha_snooze_mode: normal          # normal | math | shake | home_assistant
    fallback_grace_period: 30       # seconds to wait before falling back
    fallback_mission: block_drop
    fallback_block_drop_difficulty: hard
    fallback_block_drop_lines: 8

fallback_missionnone · shake · math · balance_ball · block_drop · meteornone
fallback_grace_periodSeconds to wait for Home Assistant first30
fallback_shake_mode · _duration · _count · _intensityAs the Shake mission's own settingsduration · 15 · 10 · medium
fallback_math_count · fallback_math_difficultyAs the Math mission's own settings3 · easy
fallback_balance_difficulty · fallback_block_drop_difficulty · fallback_meteor_difficultyeasy · medium · hardmedium
fallback_tap_dismiss_mode · fallback_tap_count · fallback_tap_hold_durationSettings for a none (Tap) fallbacktap · 1 · 3

Every fallback type takes the same settings its primary form does. A Tap fallback used to be a single tap with no settings at all; it now takes the tap fields above.

After-alarm steps

These run once the alarm is fully dismissed: the Notes page, Verse of the Day, the Morning Weather card, and finally an app link.

✅ Leaving after_alarm_actions out changes nothing. Three of the four steps have always been implied by their own fields — notes text gives a Notes page, morning_weather gives the weather card, a dismiss app link gives the open-app step. An automation that never sets this list behaves exactly as it always did. This is the sentence that stops people breaking working automations.

Send the list when you want to control the order, or to enable Verse of the Day — verse is the one step with no content of its own, so being in the list is what switches it on:

Set the after-alarm sequence 
service: allarise.update_alarm
data:
  index: 3
  after_alarm_actions: ["notes", "verse", "weather"]

Or use the single-step toggle, which is easier in an automation and appends the step to whatever sequence the alarm already has:

Turn the verse card on for one alarm 
service: allarise.update_alarm
data:
  index: 3
  verse_of_day: true
RuleWhat it means
Order is honoured, except appLinkOpen app is always forced last — it leaves Allarise, so nothing can follow it. The app's own editor enforces the same rule.
It cannot hide a step that still has contentDropping notes from the list while notes text is set does not remove the Notes page. Clear the content instead — notes: "", dismiss_app_uri: "". verse and weather have no such pull.
An empty list clears the explicit orderConfig-backed steps are re-derived, so only verse actually disappears.
Duplicates collapse, unknown ids are ignoredA typo is logged, not fatal.
List and toggle in the same callThe list is applied first, then the toggle adjusts that one step.
Reading it backThe per-alarm topic alarm/<n>/after_alarm_actions carries the sequence in run order, comma-joined, or none.
ℹ️ Verse of the Day needs an app from 28 July 2026 or later. An older app ignores the field silently — the alarm is still created or updated, just without the verse step, and nothing errors. Also worth knowing: morning_weather used to be a silent no-op on an alarm that had an explicit after-alarm order set in the app. It is not one any more.

Radio station and swipe commands

radio_station sets this alarm's wake-up station — a favourited station's name or its UUID, matched ignoring case and surrounding spaces. Send "" to clear it. It needs App Persistence on the phone; without it the alarm rings with its tone instead. For an arbitrary stream URL, publish radio_station as an object over MQTT directly.

swipe_left_command and swipe_right_command name a command to run when swiping on the alarm screen. A name that matches nothing is skipped rather than failing the whole call — a typo in an automation does not cost you the alarm. Names are matched exact-first and then forgivingly, so a stray space, a different case or a pasted invisible character still finds the command you meant.

Notes page

notes replaces the text on the after-alarm Notes page. append_notes adds a line instead — prefixed HA: and divider-separated — so a routine can build a briefing up over several steps without re-sending the whole note:

Append to the Notes page 
service: allarise.update_alarm
data:
  index: 1
  append_notes: "Bins go out tonight"
  alarm_screen_commands: ["Coffee", "Lights"]   # up to 4 buttons
💡 If the Notes page is on screen when the write lands — the alarm was just dismissed and you're still reading it — the page updates live.

allarise.create_alarm

Create a new alarm on the phone. Only the time is required — anything omitted uses the phone's own defaults, exactly as if the alarm had been created by hand. The app assigns the alarm's ID.

allarise.create_alarm 
service: allarise.create_alarm
data:
  device_name: iPhone
  time: "06:45"
  label: "Gym"
  days: [tuesday, thursday]
  sound: "Alarm_Clock"
  volume: 70
  mission: math
  mission_difficulty: medium
  snooze_duration: 9
  max_snooze_count: 2
  morning_weather: true

It takes the same fields as update_alarm — days, sound, volume, fade-in, missions, snooze and skip modes, notes, the Notes page commands, the after-alarm steps, the app links, the swipe commands and the radio station — plus two of its own:

FieldWhat it does
One-shot — ephemeralA one-shot alarm is kept out of the phone's normal alarm list and deleted automatically once it fires. It gets no per-alarm Home Assistant entities either, so there is nothing left behind to clean up — the dashboard Quick Alarm sensors are where you watch it.
MQTT ID — mqtt_idYour own stable identifier, stored alongside the alarm. Useful for finding an alarm you created from an automation later. This is not the Alarm ID that update_alarm and delete_alarm target — the app assigns that itself.

allarise.trigger_alert

Show a full-screen alert on the phone. An alert is not an alarm — there is no snooze, no mission and no recovery if the phone is off. It interrupts, plays a sound, and is gone once dismissed.

allarise.trigger_alert 
service: allarise.trigger_alert
data:
  device_name: iPhone
  title: "Motion Detected"
  message: "Front camera triggered"
  alert_id: front_door
  sound: "Perimeter_Breach"
  volume: 90                 # percent
  fade_in: 10                # SECONDS
  image_url: "/api/camera_proxy/camera.front_door"
FieldWhat it does
Alert ID — alert_idA name for this kind of alert, e.g. front_door. Sending the same ID again replaces the alert already waiting on the phone instead of adding a second one beside it — so a sensor that fires ten times leaves one notification, not ten. Omit it and the alert is identified by its title and message instead.
Play sound — play_soundWhether the alert makes any sound at all. On by default, and forced off when a Media URL is set.
Fade in — fade_inRamps the alert up over this many seconds instead of starting at full volume. The app uses 5–300 seconds; 0 starts at full volume. This is the alert's own ramp and is unrelated to an alarm's fade-in, which is in minutes.
Volume — volumeOverrides the phone's system volume for this alert, as a percentage. Alerts play through the speaker and ignore the mute switch.
Sound — soundA tone name from the phone's sound picker. Ignored when a Media URL is set, because the media replaces the tone.

The four URL fields do not behave the same way

This is the part that catches people out, so it is worth stating plainly.

FieldBehaviour
media_url, image_url, video_urlAccept a media-source ID from the media browser (media-source://…) or a path on this Home Assistant (/local/chime.mp3, /api/camera_proxy/…). Those are signed automatically, so the phone needs no token — and the signed link expires after a while, which is fine for an alert but means it is not a permanent URL. A full external URL is passed through untouched.
link_urlNot signed and not made absolute. It adds a button that opens the link in the phone's browser, so give it a complete URL the phone can reach on its own, including https://.
⚠️ Use https for external images. iOS allows plain http for audio and video but not for images — the app's transport-security exception is media-only, so an http image simply does not appear. And remember media_url replaces the alert tone: setting it forces Play sound off.

allarise.create_command

Create or update a custom command button on the phone. Creating a command whose name already exists updates it in place — the name is the key, so nothing is ever duplicated and no entity is retargeted.

allarise.create_command 
service: allarise.create_command
data:
  device_name: iPhone
  name: "Kitchen Lights"
  icon: "lightbulb.fill"
  color: "Amber"
  arm_action: none          # none | arm | disarm | toggle
  show_in_list: true
FieldWhat it does
Name — nameRequired. Also the key used to update or delete it later, and the name you reference from an alarm's swipe and Notes page buttons. Leading and trailing spaces are trimmed, so a name pasted with a stray space still matches the command you meant.
Icon — iconAn SF Symbol name, e.g. lightbulb.fill. Any SF Symbol works and nothing is validated — one this iOS version does not know simply renders as nothing. Browse and copy exact names with Apple's SF Symbols app and gallery.
Arm action — arm_actionWhat running this command does to the app's arm state, on top of whatever the command itself triggers: none · arm · disarm · toggle.
Show in list — show_in_listWhether the command appears in the app's commands list. Turn it off for one that only exists to be fired from an alarm screen or from Home Assistant.

Icon colour

The colour applies to the button's icon — the button itself is not tinted. Pick a preset name from the dropdown, or use the Custom icon colour wheel for anything else; the wheel overrides the preset.

The original twelve — these names, and the exact colour each resolves to, are frozen:
Blue Red Green Orange Purple Pink Teal Yellow Indigo Mint Brown Gray

Added in app 5.x — purely additive:
Sky Blue Cyan Navy Midnight Sea Green Forest Lime Olive Amber Gold Peach Coral Copper Sand Crimson Maroon Rose Magenta Lavender Violet Plum Slate Steel Charcoal

Names are matched case-insensitively. An older app that does not know one of the 24 newer names ignores the field and keeps the command's current colour — that has always been the behaviour for an unrecognised name, so it degrades quietly rather than erroring.

An exact colour instead of a preset 
service: allarise.create_command
data:
  name: "Kitchen Lights"
  icon: "lightbulb.fill"
  color_rgb: [255, 179, 0]     # the colour wheel

# or the individual channels, either scale:
#   color_r: 1.0   color_g: 0.7   color_b: 0.0
#   color_r: 255   color_g: 179   color_b: 0
🐞 If your custom colours came out white, this is why. The app takes 0.0–1.0 floats and older releases of this integration sent 0–255 integers, which the app clamped to full brightness. Both scales are accepted now and converted on the way out, under the same color_r / color_g / color_b keys as always — nothing you have already written needs changing.
⚡ The command's Home Assistant sensor now appears immediately. A command created over MQTT used to have no sensor until the app next reconnected. It publishes its status topic as soon as it is created, so the entity is there right away — and the command shows up in the swipe and Notes-page dropdowns at the same moment.

allarise.delete_command

Delete a custom command button by name. The field offers the commands this Home Assistant has seen the phone report; any name can still be typed. Give the name as it appears in the app's commands list — a stray space or a different case still resolves on a current app, but exact is safest.

allarise.delete_command

Example automations

Re-enable a work alarm on Sunday evening

automation.yaml 
automation:
  alias: "Re-enable work alarm on Sunday"
  trigger:
    - platform: time
      at: "20:00:00"
  condition:
    - condition: time
      weekday: [sun]
  action:
    - service: allarise.update_alarm
      data:
        index: 1              # the alarm's Alarm ID
        enabled: true

Alarms are targeted by Alarm ID, not by name — which is what keeps this automation working after the alarm is renamed on the phone.

Alert phone when front door opens at night

automation.yaml 
automation:
  alias: "Front door night alert"
  trigger:
    - platform: state
      entity_id: binary_sensor.front_door
      to: "on"
  condition:
    - condition: time
      after: "22:00:00"
      before: "06:00:00"
  action:
    - service: allarise.trigger_alert
      data:
        title: "Front Door"
        message: "Front door opened"
        alert_id: front_door        # re-fires replace, not stack
        sound: "Perimeter_Breach"
        volume: 100                 # percent

volume on this service is a percentage, 0–100. A fractional value such as 0.9 is read as 0%, which is an alert nobody hears.

Auto-snooze when leaving the bedroom

automation.yaml 
automation:
  alias: "Auto snooze when leaving bedroom"
  trigger:
    - platform: state
      entity_id: sensor.allarise_iphone_alarm_state
      to: "ringing"
  action:
    - delay: "00:00:30"
    - condition: state
      entity_id: binary_sensor.bedroom_presence
      state: "off"
    - service: allarise.snooze
      data:
        device_name: iPhone

Turn on bedroom lights 5 minutes before alarm

Every alarm's Fire Time sensor is a timestamp sensor, so Home Assistant's Time trigger can point straight at it with an offset. Home Assistant schedules a single callback at exactly the right moment and re-arms it automatically whenever you move the alarm — no polling, no template maths.

automation.yaml 
automation:
  triggers:
    - trigger: time
      at:
        entity_id: sensor.allarise_YOUR_DEVICE_alarm_1_fire_time
        offset: "-00:05:00"     # negative = before the alarm
  actions:
    - action: light.turn_on
      target:
        entity_id: light.YOUR_LIGHT
      data:
        brightness_pct: 40
        transition: 300         # fade up over the 5 minutes
  mode: single

In the UI editor this is Add trigger → Time, then Value of a date/time helper or timestamp-class sensor, pick the alarm's Fire Time, and set the offset to -00:05:00.

💡 Use a per-alarm Fire Time (…_alarm_1_fire_time) to tie the automation to one specific alarm. The dashboard Alarm Fire Time sensor tracks whichever alarm is next, so it will follow you across alarms — handy for a general "pre-wake" routine, but it also means a nap alarm will trigger it.
ℹ️ On older releases, Fire Time was a plain text sensor and this trigger would not accept it — the workaround was a Template sensor helper with Device class: Timestamp wrapping {{ states('sensor.…_fire_time') }}. That helper still works, but it is no longer needed; point the trigger at the Fire Time sensor directly. Thanks to the user who suggested this.

If you need a window rather than an instant — say "while the alarm is under 30 minutes away" — every fire-time sensor also carries a minutes_until attribute that refreshes each minute:

condition using minutes_until 
condition:
  - condition: template
    value_template: >
      {{ state_attr('sensor.allarise_YOUR_DEVICE_alarm_1_fire_time',
                    'minutes_until') | int(9999) <= 30 }}

MQTT topic structure

All topics follow the pattern {prefix}/{device}/…. With default settings, prefix is allarise and device is iphone.

DirectionTopic patternDescription
App → HAallarise/iphone/sensor/{key}Dashboard sensor values
App → HAallarise/iphone/alarm/{n}/{key}Per-alarm sensor values
App → HAallarise/iphone/availabilityApp online/offline
App → HAallarise/iphone/arm/stateArm state
HA → Appallarise/iphone/command/{cmd}Dashboard commands
HA → Appallarise/iphone/alarm/{n}/command/{cmd}Per-alarm commands
HA → Appallarise/iphone/arm/commandArm command
App → HAallarise/iphone/command/{name}/statusidle / fired for each custom command. Published as soon as the command is created — a command made over MQTT no longer waits for the app's next reconnect to get its sensor.
App → HAallarise/iphone/sensor/app_persistenceon / off, retained — whether the app is awake right now, and the receipt for the persistence command
App → HAallarise/iphone/sensor/app_persistence_modeon / off / dynamic, retained — the three-way setting the user chose

Inventory topics

Three retained topics carry a JSON array of names. They exist so Home Assistant can build dropdowns from what is actually on your phone instead of a hardcoded list:

TopicContains
sensor/alarm_sounds_availableThe phone's alarm tones. Bundled tones appear as their file id (Alarm_Clock); tones you imported appear as their name with spaces as underscores, not an internal id. Published on connect and whenever your custom tones change.
sensor/sleep_sounds_availableThe sleep sounds available on the phone
sensor/radio_stations_availableThe stations you have favourited

A sound value is resolved permissively — exact id first, then a custom tone's underscored name, then a match that ignores case, spacing and stray characters. Alarm_Clock, alarm clock and Alarm Clock all reach the same tone.

⚠️ A sound that resolves to nothing is silent about it — the alarm falls back to the phone's default tone with no error anywhere, so an alarm ringing with the wrong tone is the only symptom. Picking from the dropdown avoids it. An older app never publishes the tone list at all; the dropdown then stays empty and typeable rather than erroring, and every id still works typed by hand.
